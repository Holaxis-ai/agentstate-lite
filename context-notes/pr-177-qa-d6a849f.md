# Finding

## Medium — a late rejected display request overwrites newer successful host context

**Location:** `packages/mcp-app/src/view.ts`, `changeDisplayMode()` catch path.

Empirical sequence against the exact built App and the real `AppBridge`:

1. Start inline with fullscreen available.
2. Hold `requestDisplayMode({mode:"fullscreen"})`.
3. Emit newer host context with `displayMode:"fullscreen"`.
4. Reject the older request.

Observed result:

```json
{"button":"Return inline","status":"This host could not change the View display mode: MCP error -32603: late host rejection","statusKind":"error"}
```

The display-mode revision guard correctly prevents a stale successful result from overwriting newer
context, and the button correctly reflects fullscreen. The catch path has no corresponding revision
guard, so it overwrites the trusted shell’s live status even though newer host context already
established success.

This violates the reviewed criterion in
`context-notes/pr-177-fullscreen-plan-review`: “Host context reports target before a late request
rejection; stale rejection does not destroy or overwrite the live View.” It also confirms the
residual risk called out by `context-notes/pr-177-rereview-d6a849f`.

Required correction: when display-mode context advanced after the request began and establishes the
requested mode, treat the older rejection as stale for status presentation. Add a browser regression
for this exact sequence. Do not couple this presentation decision to durable launch authority.
