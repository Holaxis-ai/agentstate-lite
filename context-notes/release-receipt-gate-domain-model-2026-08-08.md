# Summary

This is the implementation domain model for the P5A receipt-gate fix delta after Brian's 2026-08-08 rulings. The ultimate goal is safe protected npm distribution with human-controlled publication. The proximate goal is to close the P5A findings and produce a reviewed, PR-ready feature branch, clearing P5B -> P5S -> continuous staging. The next action is one builder unit that integrates current main, implements the actor and asset-inventory corrections with tests, and yields an exact SHA for independent review.

The governing distinction is: mutable-draft tolerance is not publication authority. Stale sibling-stage evidence may coexist on a reused draft long enough for the current candidate to be verified, but only the exact core assets, verified current-stage receipts, and (when policy requires it) the exact status stamp generated by the current finalizer may survive into the published release.

# Terms and identities

- **Candidate identity**: `stage_id + version + tarball_sha256 + draft_release_id`. Every operator receipt binds exactly this tuple. Brian confirmed that `run_id` is deliberately absent so a valid receipt survives a legitimate finalize redispatch.
- **Finalize-run identity**: the separately dispatched GitHub Actions run. Its GitHub-attested `created_at` bounds which already-uploaded receipts it may consume. Its run ID belongs in a generated status stamp, not in the signed candidate-binding tuple.
- **Current stage**: the stage ID that agrees across workflow dispatch, retained stage receipt, and verified finalizer chain. A filename suffix alone never establishes current-stage identity.
- **Sibling stage**: a syntactically valid stage ID different from the verified current stage, found on the same mutable draft after a prior rejected/replaced attempt. It is historical residue, not evidence for the current candidate.
- **Receipt**: signed JSON with schema `aslite.operator-receipt.v1`, decision `inspected` or `approved`, the candidate identity, one operator identity, and emission time. An inspection receipt also binds the observed SHA-256. The signed canonical bytes omit `run_id`.
- **Status stamp**: unsigned JSON with schema `aslite.receipt-status.v1`, derived only from a verified ordering result when live prerelease policy tolerates missing receipt evidence. Its authority comes from current-finalizer generation plus final byte/digest verification, never from its filename alone.
- **Core asset**: the retained tarball and `candidate.json`, whose names, IDs, and digests are fixed in the stage receipt.
- **Current decision asset**: the unique exact name `receipt-{inspected|approved}-<currentStageId>.json`; it becomes publication-eligible only after signature, binding, signer, uploader, and time/order verification.
- **Current status asset**: `receipt-status-<currentStageId>.json`. A pre-existing copy is untrusted replacement input. It is publication-eligible only if this finalizer requires a stamp, generates the expected bytes, uploads them retry-safely, and the final inventory re-proves those bytes.
- **Sibling auxiliary asset**: an exact receipt/status grammar with a valid sibling stage ID. It may be tolerated on the draft but is ignored as evidence and must be removed or otherwise excluded before publication.
- **Malformed or arbitrary receipt-shaped asset**: any lookalike that lacks an allowed decision, exact grammar, or valid stage-ID suffix. It is an ordinary unexpected extra and fails closed; it is not granted auxiliary status.

# Actors and trust boundaries

- **Inspector**: Brian or Mike, identified by the allowed-signers principal, signed payload actor, and matching GitHub asset uploader. Downloads the staged tarball and attests its observed checksum.
- **Approver**: Brian or Mike, independently identified by the approval receipt. Brian ruled that inspector and approver may differ. The per-receipt signer/uploader equality remains mandatory; only cross-receipt equality is removed.
- **npm human approval**: the external `npm stage approve` plus 2FA act. The approval receipt records the operator evidence; it does not create another GitHub approval button.
- **Finalize workflow**: may verify signatures and candidate bytes, generate an unsigned missing-evidence stamp, normalize the draft's final asset inventory, and publish. It cannot impersonate a human receipt signer.
- **GitHub `contents:write` principal**: can mutate the draft and therefore cannot make a claim trustworthy merely by choosing a receipt-shaped filename. All current receipts are cryptographically and metadata verified; all other auxiliary assets are excluded from final publication.
- **Committed `.github/release-allowed-signers`**: the public-key trust root. Code/tests can verify syntax and expected principals, but Brian must personally verify that the listed Brian/Mike keys are the intended keys during PR review.
- **npm/GitHub APIs**: external facts for stage/publication state, draft identity, uploader identity, timestamps, and asset digests. Inputs remain untrusted until they agree with retained identifiers.

# Release-state identity model

The reconciler's immutable identifier map must retain actor identity per lifecycle step, not under one global `actor` key. Use state-specific ledger fields such as `inspected_by`, `approved_by`, `rejected_by`, `promoted_by`, and `rolled_back_by` (or one equivalently explicit per-state mapping). The external signed receipt remains `actor`; the ordering adapter maps it into the state-specific ledger field.

This preserves two invariants simultaneously:

1. Replaying the same state with a different actor is an identifier mismatch.
2. Different legal states may name different allowed operators without contradiction.

`evaluateOrdering` must remove only the inspection-actor-equals-approval-actor rule. It must retain signer allowlisting, signed actor equals uploader, upload-before-finalize-dispatch, and inspection-upload-before-approval-upload when both receipts exist. Its proof must expose per-decision actor identity (`actors.inspected` and `actors.approved`, with null for missing evidence) instead of collapsing identity to one actor.

For a prerelease with approval but no inspection, Brian's ruling permits publication with the verified approval receipt plus the missing-inspection stamp. The lifecycle ledger remains at `staged` because no `inspected` transition can be replayed; the ordering proof separately records `verified: [approved]`, `actors.approved`, `missing: [inspected]`, and `stamp_required: true`. `state` is therefore the last reconciled lifecycle state, not the full policy verdict. Stable policy still rejects the same evidence shape.

# Asset inventory state machine

## Draft verification phase (read-only)

1. Verify the exact two core assets against the retained stage receipt.
2. Classify every extra asset relative to the verified current stage.
3. Current inspected/approved assets are selected uniquely and must pass the full receipt verification path.
4. Current status and valid sibling auxiliary assets are recorded as untrusted/residual inventory, never consumed as current evidence.
5. Malformed receipt lookalikes and ordinary extras fail closed.

This phase may tolerate recognized sibling residue so a reused mutable draft remains operable. Tolerance means "ignore as current evidence and schedule exclusion before publish," not "allow onto the immutable release."

## Publication-normalization phase (write-capable finalizer)

1. From the ordering result, establish the exact publication allowlist: core two; whichever current decision receipts were actually verified; and a current status stamp iff `stamp_required`.
2. Remove/exclude every sibling auxiliary asset and every unverified current auxiliary asset before publication.
3. If no stamp is required, ensure no current status asset remains.
4. If a stamp is required, generate it from the current ordering result and upload with `--clobber`; a pre-existing same-name asset is replacement input, never accepted evidence.
5. Re-query the draft immediately before publication and prove exact final inventory. Receipt IDs/digests must match the assets that were verified. A status asset must match the just-generated file's digest. No sibling or arbitrary auxiliary asset may remain.
6. Only after that final proof may `immutable-release` publish the draft.

This makes retries safe: a prior failed finalize may have left a same-name current status asset, but a required stamp replaces it; a clean/no-stamp path removes or rejects it. It also prevents a forged status from riding unchanged and prevents arbitrary tolerated sibling assets from becoming permanent published artifacts.

# Policy matrix

| Tier/evidence | Result | Ledger | Published evidence |
|---|---|---|---|
| Prerelease, both valid (same or split operators) | allow | `approved_public` | both verified receipts; no status |
| Prerelease, approved only | allow | `staged` | approval receipt + generated missing-inspection status |
| Prerelease, inspected only | allow | `inspected` | inspection receipt + generated missing-approval status |
| Prerelease, neither | allow | `staged` | generated status naming both missing receipts |
| Stable, both valid (same or split operators) | allow | `approved_public` | both verified receipts; no status |
| Stable, either missing | reject | last reachable state | draft remains unpublished |
| Either tier, any present current receipt invalid | reject | none published | draft remains unpublished |
| Either tier, current forged/pre-existing status | never trusted | policy-dependent replacement/removal | cannot ride unchanged |
| Either tier, sibling auxiliary residue | ignored during draft verification | no effect | excluded before publication |
| Either tier, malformed/arbitrary extra | reject | no effect | draft remains unpublished |

# Ordering and timing invariants

- Candidate binding equality is checked before receipt evidence affects policy.
- Each current decision receipt is unique by exact name.
- The signed actor is allowed and equals that asset's GitHub uploader.
- Receipt assets were uploaded no later than the current finalize run's GitHub creation time; later evidence requires redispatch.
- When both receipts exist, inspection upload precedes approval upload; their actors may differ.
- Missing evidence is policy input; invalid evidence is always fatal.
- `run_id` is intentionally absent from signed candidate binding; `finalize_run_id` appears only in a generated status stamp.
- The final asset inventory is re-queried and verified after cleanup/clobber and immediately before publication.
- Dry-run never mutates, stamps, cleans, or publishes; it reports what live policy would do and still rejects present-invalid evidence.
