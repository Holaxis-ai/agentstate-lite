## The news

MCP published spec revision `2026-07-28` on schedule (RC announced 2026-05-21). It is the
largest revision since the protocol launched: protocol-level sessions are deleted, the
`initialize` handshake is gone, server-initiated requests (elicitation, sampling, roots) are
replaced by a retry-based pattern, and MCP Apps — the thing our `aslite mcp` command is built
on — graduates from experiment to an official, independently versioned extension.

## Why it costs us almost nothing

Two reasons, one lucky and one earned.

**The lucky one: we cannot adopt it yet even if we wanted to.** The TypeScript SDK's latest
published release (`1.30.0`) still declares `2025-11-25` as its protocol version. Nothing to
migrate onto; nothing to decide this month. I verified this against the published tarball
rather than the copy in our `node_modules`.

**The earned one: the spec moved toward our design, not away from it.** The headline change is
that servers can no longer rely on a protocol session, and the spec's prescribed replacement is
"explicit, server-minted handles passed as ordinary tool arguments." That is precisely what our
MCP adapter already does — every launch, bridge call, approval, and action is keyed by a
server-minted `launchId` passed as a tool argument. We arrived there for security reasons; it
turns out to also be the forward-compatible shape.

Three more places where a change that broke other people's servers does not reach us:

- **Elicitation was restructured out from under its users.** We never used it — human
  confirmation for writes lives in our own trusted shell chrome via app-only prepare/finish
  tools. That call now looks better than it did when we made it.
- **Logging is deprecated**, with stderr-for-stdio as the recommended migration. That is
  already our standing gate, because stdout is the JSON-RPC transport.
- **Roots, sampling, tasks, resource subscriptions, SSE resumability** — all changed, none used
  by us.

Also worth saying plainly, since the two are easy to conflate: **our own wire protocol
(`packages/server`, `docs/WIRE-PROTOCOL.md`) has nothing to do with MCP and is untouched.** So
is the `ui` command and everything under it. The gate-4 discipline — one View semantics and
action authority, with host-specific adapters over it — is exactly what contained this. The
largest MCP revision since launch lands on the adapter and leaves the authority alone. That is
the first real test of that architectural claim, and it held.

## What it will cost us, when the SDK catches up

One unit of work, small, mostly mechanical:

1. Advertise the Apps extension under its new identifier (`io.modelcontextprotocol/ui`) in the
   new `server/discover` RPC. Probably free — the Apps SDK should own it; verify rather than
   assume.
2. Add the now-required `ttlMs`/`cacheScope` fields to our one served resource and our tool
   list. Our shell resource is content-addressed by digest, so long-cache is correct by
   construction.
3. Make our three model-visible tools degrade cleanly for hosts that do not support the Apps
   extension. We already return meaningful text, so this is really one wart: `show_view`
   unconditionally appends an internal claim marker to that text, which is noise for a
   non-Apps host.
4. Rename internals that say "session" — the word now means something in the protocol that no
   longer exists, and what we actually mean is process-scoped.

Everything we depend on at the wire level (`_meta.ui.resourceUri`, `_meta.ui.csp`, `ui://`
resource URIs) is unchanged, because the Apps extension versions independently of the core
protocol. That independence is the reason this revision is a chore rather than a rewrite.

## What I would like you to weigh in on

1. **Decline the host-mediated confirmation path.** The new multi-round-trip pattern is the
   standards-track way to have the *host* prompt the human for confirmation instead of our own
   app chrome. My recommendation is to not take it: our trust argument depends on the
   confirmation being rendered in chrome we authored and can reason about, outside the
   generated frame. A generic host dialog weakens the claim we actually make. Want this
   recorded as considered-and-declined rather than never-noticed.
2. **No dual-protocol compatibility layer.** When the SDK ships the new revision, take the
   break. The MCP surface is experimental, local, stdio-only, unpublished as a package, and
   has no external consumers — carrying a compatibility layer would be real complexity bought
   for nobody.
3. **Minor:** `cacheScope` on the shell resource. `"public"` is defensible (it is not user
   data); `"private"` is the conservative default and costs us nothing on a local stdio server
   where there is no shared cache to benefit. I lean private.

## One thing to remember later, not now

If we ever put the MCP surface on HTTP (not planned, not proposed), stateless makes
multi-instance routing the default assumption, and our launch/authorization state is
per-process and unverifiable off-box. The handles would need to become signed and verifiable,
or move to a shared store, before that is safe. Recording it so it is a known precondition
rather than a surprise.

## Recommended posture

Do nothing, deliberately, with an explicit trigger: the first `@modelcontextprotocol/sdk`
release whose protocol version is `2026-07-28`, plus a matching Apps SDK release. Until then
there is genuinely nothing to do, and the deprecations all carry twelve-month windows under
the new lifecycle policy, so there is no cliff behind them either.
