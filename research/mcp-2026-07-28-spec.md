Assessment of the MCP `2026-07-28` specification revision (release candidate announced
2026-05-21, final publication 2026-07-28) against this repo's MCP surface, `packages/mcp-app`
plus the `aslite mcp` command. Sources: the spec changelog, the extensions overview, the MCP
Apps extension docs, and the installed/published SDK artifacts (verified 2026-08-03).

## Bottom line

Nothing is broken and nothing is urgent. The TypeScript SDK cannot speak this revision yet:
`@modelcontextprotocol/sdk` at latest published `1.30.0` still declares
`LATEST_PROTOCOL_VERSION = '2025-11-25'` (verified by unpacking the published tarball, not by
reading the installed `1.29.0`). `@modelcontextprotocol/ext-apps` is unchanged at `1.7.5`.
Our exposure is a **future migration gated on the SDK**, not a live break.

The most consequential finding is not a risk, it is convergence: the revision's central
architectural move -- delete protocol-level sessions, and have servers that need cross-call
state use **explicit, server-minted handles passed as ordinary tool arguments** -- is exactly
the shape `packages/mcp-app` already has (`launchId` + the launch/authorization registries).
The spec moved toward our design, not away from it.

## Per-change assessment, ranked by what it costs us

### 1. Stateless lifecycle (SEP-2575, SEP-2567) -- low risk, high validation

`initialize`/`notifications/initialized` and `Mcp-Session-Id` are gone. Protocol version,
client capabilities, and client info now ride `_meta` on every request
(`io.modelcontextprotocol/protocolVersion`, `.../clientCapabilities`, `.../clientInfo`), and
`server/discover` becomes a MUST-implement RPC for version/capability/identity advertisement.

We are stdio, single-process, and never touched `Mcp-Session-Id`. The handshake is SDK-owned,
so this lands with an SDK bump. Our cross-call state already follows the spec's prescribed
replacement.

Residual item: **naming debt**. `SessionViewAuthorizationStore`, and the "session-scoped"
language around trust in code and in CLAUDE.md, now collide with a protocol term that no
longer exists. The scope we actually mean is process/invocation-scoped. Rename when we touch
the file; do not open a unit for it alone.

### 2. Extensions framework, Apps as an official extension (SEP-2133, SEP-1865) -- moderate, mechanical

Extensions are now formal, reverse-DNS identified, independently versioned, opt-in, and
negotiated. The Apps extension identifier is **`io.modelcontextprotocol/ui`**, with a settings
object of `{ "mimeTypes": ["text/html;profile=mcp-app"] }`; servers advertise it under
`capabilities.extensions` in the `server/discover` result.

The wire shapes we depend on are **unchanged**: `_meta.ui.resourceUri`, `_meta.ui.visibility`,
`_meta.ui.csp`, and `ui://` resource URIs are all still current in the live Apps docs. Apps
versions independently of core (current Apps spec revision `2026-01-26`), which is precisely
why the core revision does not disturb us. Our `_meta: { ui: { ... } }` on every
`registerAppTool`/`registerAppResource` call stays correct as written.

Two obligations arrive with negotiation:

- The server must advertise `io.modelcontextprotocol/ui` in `server/discover`. Expect
  `ext-apps` to own this; verify rather than assume when the SDK lands.
- Extensions MUST degrade gracefully: "a server offering UI-enhanced tools should still return
  meaningful text content for clients that don't support the UI extension." We already do
  (`fallbackText(payload)`). One wart: `show_view` appends the one-shot claim marker to that
  text unconditionally. For a non-Apps host that marker is unusable noise. Once per-request
  client capabilities are readable, gate the marker on the client actually advertising the ui
  extension.

### 3. `CacheableResult`: `ttlMs` + `cacheScope` now required (SEP-2549) -- small, but ours to decide

Required on `tools/list`, `prompts/list`, `resources/list`, `resources/read`, and
`resources/templates/list`.

We serve exactly one resource: `ui://agentstate/view-host/v1/<digest>.html`. It is
content-addressed by digest and carries no bundle data, so a long `ttlMs` is both safe and
correct -- a changed shell changes the URI. On `cacheScope`: the shell HTML is not user data,
so `"public"` is defensible, but for a local stdio server there is no shared intermediary to
benefit, and `"private"` is the conservative default that cannot leak a future mistake. Take
`"private"` unless someone argues the caching win.

`tools/list` is fixed per process, so a high `ttlMs` is fine there too. The same SEP adds a
SHOULD for deterministic `tools/list` ordering; we register in fixed source order and already
satisfy it.

### 4. Multi Round-Trip Requests replace server-initiated requests (SEP-2322) -- validates our action design

Server-initiated `elicitation/create`, `sampling/createMessage`, and `roots/list` are replaced
by the MRTR pattern: the server returns an `InputRequiredResult` (`resultType:
"input_required"`) carrying `inputRequests` plus `requestState`, and the client retries the
original request with `inputResponses`. `notifications/elicitation/complete` and the
`elicitationId` field are removed outright.

We never used elicitation. Human confirmation for `document.set-field` lives in trusted shell
chrome, mediated by the app-only `prepare_view_action` / `finish_view_action` pair. That
choice now looks better than it did: the surface we would otherwise have built on has been
restructured out from under its users.

MRTR does open a legitimate future option -- a **host**-mediated confirmation instead of an
**app**-mediated one. Recommend recording it as considered and declined: our trust argument
depends on the confirmation being rendered in chrome we authored and can reason about, outside
the generated frame. A generic host dialog weakens the claim we actually make in gate 4.

### 5. Deprecations: Roots, Sampling, Logging (SEP-2577) -- no exposure

Twelve-month removal windows; all three remain functional. We use none of them. The suggested
migration for Logging is stderr for stdio -- which is already our standing gate ("`mcp` routes
every startup or runtime envelope to STDERR because stdout is the JSON-RPC transport"). Also
deprecated: HTTP+SSE transport, `includeContext` values `thisServer`/`allServers`, and OAuth
Dynamic Client Registration in favour of Client ID Metadata Documents. None reach us.

### 6. Subscriptions: `subscriptions/listen` replaces the GET stream and `resources/subscribe` -- no exposure

Our durable bridge polls (`enablePolling: true`, the app-only `poll_durable_view` tool), and
that polling rides the Apps postMessage dialect rather than core MCP resource subscriptions.
Unaffected in either direction.

### 7. Tasks moves to `io.modelcontextprotocol/tasks` (SEP-2663) -- no exposure

We do not use tasks. Noted only so a future "make show_view async" idea starts from the
extension, not from the removed core feature.

### 8. Full JSON Schema 2020-12 for tool schemas (SEP-2106) -- opportunity, not obligation

`inputSchema`/`outputSchema` may now use any 2020-12 keywords (`oneOf`, `anyOf`, `allOf`,
conditionals, `$ref`), and `structuredContent` may be any JSON value.

`show_view`'s input is genuinely a discriminated union -- exactly `viewId`, or `title`/`html`
plus exactly one generated selection mode. Today that union is a flattened all-optional
`.strict()` object with the constraint stated in prose in `.describe()`, enforced at runtime by
`parseShowViewInput`. With 2020-12 we could express it as `oneOf` so hosts and models see the
shape instead of discovering it through error messages.

Counterweight worth stating plainly: a more capable schema moves validation toward the client,
and our security posture requires the server-side parse to remain the authority. Do both --
publish the `oneOf`, keep `parseShowViewInput` exactly as strict as it is now.

### 9. Error code allocation policy (SEP-2164 and the `-32020`..`-32099` reservation) -- no change

We emit no custom JSON-RPC error codes; our capped taxonomy is the CLI's exit codes, which is
a different layer entirely.

### 10. Transport hardening -- no exposure today, raises the bar on a future HTTP surface

SSE resumability and message redelivery (`Last-Event-ID`, SSE event IDs) are removed: a broken
stream loses the in-flight request and the client must re-issue with a new request ID.
`Mcp-Method`/`Mcp-Name` headers become required on Streamable HTTP POSTs. Stdio-only means none
of this reaches us now.

## What is explicitly NOT affected

- **`packages/server` and `docs/WIRE-PROTOCOL.md`.** Our wire protocol is our own; it has no
  coupling to MCP and this revision does not touch it. Worth saying out loud because the two
  are easy to conflate.
- **The `ui` command, bundle Views, `view-runtime`, `markdown-renderer`.** Host-neutral by
  construction. Gate 4's claim -- one View semantics/action authority, host-specific adapters --
  is what insulates us here: the largest MCP revision since launch touches the adapter and
  leaves the authority alone. This release is the first live test of that claim, and it holds.

## The one real architectural note

If we ever expose the MCP surface over Streamable HTTP (not planned, not proposed), the
stateless revision makes multi-instance routing the default assumption. Our launch and
authorization state is per-process and unverifiable off-box, so the spec's own guidance
(server-minted handles as tool arguments) would have to become *signed and verifiable* handles,
or move to a shared store, before that is safe. Stdio single-process makes this a non-issue
today. Recorded so it is a known precondition rather than a discovery.

## Recommended posture

Do nothing now, deliberately, and make the trigger explicit rather than relying on someone
noticing.

1. **Trigger:** the first `@modelcontextprotocol/sdk` release whose `LATEST_PROTOCOL_VERSION`
   is `2026-07-28`, plus a matching `ext-apps` release. Until then there is nothing to migrate
   onto.
2. **When it lands, one unit:** bump the SDK; verify `server/discover` advertises
   `io.modelcontextprotocol/ui`; add `ttlMs`/`cacheScope` to the view resource and tool list;
   gate the claim marker on advertised client capability; rename the session-named internals;
   optionally express `show_view`'s input as `oneOf` while keeping the server-side parse
   authoritative.
3. **Then fix the prose** -- CLAUDE.md gate 4's "session" language follows the code, not the
   other way round.

Because our MCP surface is explicitly experimental, local, stdio-only, unpublished as a
standalone package, and not a supported product surface, we have full freedom to take the
break when it comes. **Do not build a dual-protocol compatibility layer** -- that would be
carrying real complexity for a surface with no external consumers.
