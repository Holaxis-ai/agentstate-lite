# Executive conclusion

OpenCode exposes useful pieces of a checkpoint lifecycle, but the installed runtime and the current `agentstate-lite` adapter do not provide the full lifecycle required by the shared domain model.

- **Full checkpoint lifecycle:** unsupported. The strict blocker is semantic capture: OpenCode's compaction request is performed by a hidden `compaction` agent with tools disabled, not by the original bearer that holds unwritten understanding. Root-stop and child-stop boundaries are also post-hoc or absent, and host plugin hooks have no timeout/fail-open contract.
- **Capture-only:** unsupported under invariant S2. OpenCode does generate a rich continuation summary from the serialized transcript, but it is generated by the hidden compaction agent and stored in OpenCode's session state, not written to the bundle by the original bearer.
- **Restore-only:** conditionally feasible as an adapter design. `experimental.chat.system.transform` is awaited before a provider request and receives a `sessionID`, so it can inject an already-current, bounded checkpoint. The design must add exact identity evidence, revision selection, local timeout/fail-open behavior, size bounds, and causal delivery receipts.
- **Inspectable/manual:** supported and is the strongest honest present behavior. Checkpoint documents can remain inspectable in the bundle and an operator or agent can request/use them manually. The current adapter injects session-start orientation once per plugin-session key, but is not compaction-aware.
- **Current product behavior:** the generated OpenCode plugin only runs `session-start` through `experimental.chat.system.transform`, caches by `sessionID`, and injects the result. It does not observe compaction, capture a semantic checkpoint, invalidate on compaction, or restore an exact checkpoint revision.

The runtime-neutral protocol should therefore treat OpenCode as an adapter with a **conditional pre-loss notification**, a **conditional pre-request injection point**, and no proven same-bearer semantic-capture primitive. The protocol must not redefine OpenCode's hidden summarizer as same-bearer capture merely to make the matrix appear complete.

# Ordering and payload facts

For I, manual and automatic compaction share this relevant order:

1. A compaction user part is persisted with its `auto` flag.
2. The session prompt loop selects the pending compaction part before a normal step.
3. OpenCode creates the hidden compaction-agent assistant message in the same session.
4. It awaits every `experimental.session.compacting` named hook in plugin load order. Payload: `{sessionID}`. Mutable output: `{context: string[], prompt?: string}`.
5. It calls the model with tools disabled, the transformed serialized message history, and either the default summary prompt or plugin replacement prompt/context.
6. On successful automatic compaction, it appends a synthetic continuation request. Manual compaction does not add that automatic continuation.
7. It publishes `session.compacted` with only `{sessionID}` and returns control to the prompt loop.
8. Before each later provider request, OpenCode awaits `experimental.chat.system.transform`; this is the last reliable adapter injection gate exposed by the V1 hook contract.

Important failure/ordering qualifications:

- Named trigger callbacks are awaited sequentially and have no host timeout.
- Plugin event callback promises are intentionally not awaited by the plugin subscriber, so `session.compacted` cannot be a completion barrier.
- Terminal prompt-loop exit produces idle/status after the fact. It is not a before-stop checkpoint barrier.
- The same plugin module can serve multiple sessions and child sessions; process-global caches are therefore concurrent shared state.
- S introduced `experimental.compaction.autocontinue`, but that does not change the missing original-bearer semantic-capture primitive.

# Existing adapter delta

At A, `packages/cli/src/commands/hook.ts` generates an OpenCode plugin with:

- an exact-byte-owned file named `axi-agentstate-lite.js`;
- one hook, `experimental.chat.system.transform`;
- a process-global `Map` keyed by `sessionID` or the ambiguous fallback `__global__`;
- one `session-start` child execution per cached key;
- a 10-second helper timeout and nonthrowing error-string fallback;
- ambient injection by appending the helper output to the system array.

This establishes a valuable installation/restore-adjacent base, but the checkpoint design must change the semantics before claiming lifecycle support:

1. Replace `__global__` and bare session-key assumptions with an explicit scoped identity/lineage record.
2. Treat compaction events as invalidation hints only; perform current-revision selection at the awaited request transform.
3. Add a bounded payload contract, revision/CAS selection, and delivery receipts.
4. Add explicit health/degradation status and retry/expiry policy rather than caching an error forever.
5. Do not add automatic capture until there is an honest same-bearer synthesis route or the shared S2 invariant is explicitly changed by a design decision.

# Version and migration caution

The installed I runtime and latest stable S are V1-style implementations. D contains a V2 session specification and V2 compaction documentation. The V2 spec marks per-turn plugin message/system/parameter/header transforms as missing at the inspected revision. Therefore a design based on V1 hooks must be version-gated and must re-probe V2; it must not infer that V1 plugin contracts survive the migration.

# Design-plan probes, prioritized

1. **P0: semantic-capture adjudication.** Decide whether S2 remains strict. With S2 unchanged, classify OpenCode automated capture as unsupported; do not spend implementation effort pretending the compaction agent is the original bearer.
2. **P0: post-loss injection oracle.** Pin I in isolated XDG roots with an instrumented provider; prove `system.transform` completion and exact checkpoint revision precede the first dependent provider request.
3. **P0: bounded failure harness.** Resolve/reject/hang hooks and absent/crash/hang/oversized helper cases; verify adapter-local timeout, host continuity, durable dirty/failure status, and no false acknowledgement.
4. **P1: identity/lineage harness.** Cover compaction, process restart and resume, fork, two sibling child sessions, and duplicate concurrent resume. Establish project/session/parent/execution keys and collision rules.
5. **P1: event race harness.** Delay `session.compacted` handlers past the next request and prove the design does not depend on event completion ordering.
6. **P1: install lifecycle matrix.** Validate absent/exact/stale/foreign/alternate-dir/disable/uninstall states with byte-for-byte preservation of foreign files.
7. **P2: privacy and payload boundary sweep.** Verify logs/receipts are content-free and injection is bounded, escaped, and visibly truncated.
8. **P2: V2 gate.** Before supporting V2, repeat the matrix against the shipped V2 release rather than relying on current dev documentation.

# Assumptions that remain explicitly unverified

- A stored V1 session can be resumed after a complete host-process restart with the exact same session ID in all supported CLI/server entry paths.
- Two simultaneous carriers attached to one V1 session are either prevented or have a deterministic ordering visible to the adapter.
- Host cancellation terminates a named plugin hook that never settles; source exposes no abort signal and does not prove termination.
- Numeric maximums and encoding behavior for transformed system strings and plugin/helper output.
- Exact event sequences for hard process death, terminal provider error, and parent-child cancellation races.
- Credential/environment behavior under representative user installations; source establishes inheritance risk, not every deployed secret surface.
- Any V1 hook compatibility in the future V2 runtime.

These unknowns are design inputs and test obligations, not permission to infer support.
